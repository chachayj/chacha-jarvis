미결 · 보안

멤버 초대 전에 처리해야 하는 항목

SECRET_KEY가 공개된 기본값이다

현재 SECRET_KEY가 60gp0byfz2dv…인데, 이 값은 Plane v1.2.1 docker-compose.yaml에 하드코딩되어 배포되던 공개적으로 알려진 기본값이다. 설치 시 .env로 그대로 복사되었고 v1.4.2로 올린 뒤에도 남아 있다.

Django가 기동 시 직접 경고를 낸다 — 세션 위조, CSRF 우회, 비밀번호 재설정 토큰 위조가 가능하다. Plane은 v1.4.0에서 이 기본값을 제거했지만, 제거된 것은 compose의 fallback이지 우리 .env에 박힌 값이 아니다.

교체하면 기존 로그인 세션만 끊긴다(재로그인 필요). 데이터는 무사하다. 비밀번호 해시는 SECRET_KEY와 무관하고, API 토큰은 v1.4.0부터 SHA-256 해시로 저장되므로 영향받지 않는다. 

# 새 키 생성
docker exec plane-image-api-1 python -c \
  "from django.utils.crypto import get_random_secret_key; print(get_random_secret_key())"

# .env의 SECRET_KEY 교체 후 재기동
cd /home/plane/plane/plane-image
docker compose up -d

같은 맥락에서 .env에는 SECRET_KEY와 LIVE_SERVER_SECRET_KEY가 평문으로 들어 있고 레포에 커밋된다. 정리할 거면 두 값을 함께 회전시키고 .env를 gitignore + .env.example 방식으로 빼는 게 맞다 — .mcp.json에 적용한 것과 같은 패턴이다.

네트워크 경로

팀원 브라우저에서 데이터 파일까지

이 배포에서 가장 헷갈리는 지점은 WSL2가 NAT 뒤에 있다는 것이다. 컨테이너가 8080을 열어도 그것은 WSL 내부 주소 (172.19.98.53)에 열리는 것이라, LAN의 다른 PC는 192.0.2.10:8080으로 닿을 수 없다. Windows 쪽에 포트포워딩을 놓아야 비로소 경로가 이어진다.

mirrored 모드는 이 데탑에서 못 쓴다

WSL2 networkingMode=mirrored를 쓰면 portproxy가 필요 없지만 Windows 11 (build 22000+) 전용이다. 이 데탑은 Windows 10 build 19045라 해당되지 않는다. 설정 스크립트도 빌드 번호를 확인해 Windows 10이면 중단한다.

레포 구조 · 두 스택

운영과 실험이 완전히 분리되어 있다

Plane을 돌리는 방식이 두 가지다. 공식 이미지를 받아 쓰는 운영 스택과, 소스에서 직접 빌드하는 실험 스택. 폴더가 다르고 포트·데이터·시크릿이 전부 갈라져 있어 한쪽에서 무슨 짓을 해도 다른 쪽에 영향이 없다.

plane-image 운영plane-src 실험
이미지artifacts.plane.so에서 pull로컬 빌드 myorg/plane-*
포트8080 / 4438081 / 8444
데이터plane-image/data/plane-src/data/
컨테이너plane-image-*plane-src-*
태그v1.4.2v1.4.2-custom.1
시크릿별개별개 (새로 생성)

컨테이너 이름은 compose 프로젝트명이 폴더명에서 나오므로 자동으로 갈린다. 메모리는 15Gi 중 12Gi가 여유라 두 스택을 동시에 띄워도 된다 (현재 운영 스택 전체가 1.6Gi). 

plane/
  setup.sh
  plane-image/         운영 — 공식 이미지
    docker-compose.yaml  .env  data/
  plane-src/           실험 — 소스 빌드
    build.yml            이미지 6개 빌드 정의
    docker-compose.yaml  .env  data/
    src/                 Plane v1.4.2 원본 ← 수정은 여기서

src/ 는 무수정으로 시작한다

build.yml을 원본 위치(src/deployments/cli/community/)에서 그대로 쓰지 않고 따로 둔 이유가 이것이다. 원본은 build context가 ../../인데 여기서는 ./src여야 한다. 원본을 고치면 나중에 “내가 고친 것”과 “경로 맞추려고 고친 것”이 diff에서 섞인다. 인프라 설정은 src/ 바깥에 둔다.

소스 빌드 · 기동

cd plane/plane-src

docker compose -f build.yml build           # 전체 6개
docker compose -f build.yml build api web   # 수정한 것만

docker compose up -d                        # :8081 로 기동

plane-backend 하나를 api·worker·beat-worker·migrator가 공유하므로 API를 고치면 그 넷이 함께 바뀐다.

버전 태그 규칙

v{upstream}-myorg.{n} — 예: v1.4.2-custom.1. upstream 버전을 반드시 남긴다. 지금 도는 게 어느 기반인지 알아야 보안 패치를 따라갈 수 있다. local 같은 태그는 몇 달 뒤 추적 불가능해진다.

clone 하려면 git-lfs가 필요하다

plane-src/src/의 이미지·폰트 411개(약 30MB)가 Git LFS로 저장되어 있다. git-lfs 없이 clone하면 이미지 대신 포인터 텍스트가 받아져 빌드가 깨진다. 

sudo apt install git-lfs && git lfs install

# sudo가 안 되면 — 바이너리를 홈에 두면 된다
curl -sSL -o /tmp/lfs.tar.gz \
  https://github.com/git-lfs/git-lfs/releases/download/v3.8.0/git-lfs-linux-amd64-v3.8.0.tar.gz
tar -xzf /tmp/lfs.tar.gz -C /tmp
mkdir -p ~/.local/bin && cp /tmp/git-lfs-*/git-lfs ~/.local/bin/
export PATH="$HOME/.local/bin:$PATH"
git lfs install --skip-repo

이미 git-lfs 없이 clone했다면 설치 후 git lfs pull로 실제 파일을 받는다. LFS를 쓰는 이유는 upstream 업그레이드마다 src/를 통째로 교체하는데, LFS가 없으면 그때마다 바이너리 30MB가 히스토리에 영구 누적되기 때문이다.

upstream 업그레이드

소스를 복사해 넣었으므로 git이 병합을 도와주지 않는다. 수동 절차다. 새 릴리즈를 별도로 클론하고, git log -- plane/plane-src/src/로 우리가 고친 파일을 확인한 뒤, 새 소스로 교체하고 그 수정을 다시 적용한다. 수정 파일이 늘어날수록 무거워진다 — 고치기 전에 설정·API로 안 되는지 먼저 볼 것.

Plane 이미지 8종은 전부 ${APP_RELEASE}를 참조하므로 .env 한 줄로 전체 버전이 따라 움직인다. 레지스트리는 artifacts.plane.so/makeplane을 쓴다 — 공식 v1.4.2 compose는 Docker Hub를 쓰지만, 익명 pull 제한을 피하려고 유지했다.

minio/minio:latest는 태그가 고정되어 있지 않다. 컨테이너를 재생성할 때마다 상위 버전이 딸려올 수 있으니, 언젠가 특정 태그로 고정하는 게 좋다.

데이터와 이식

named volume이 아니라 bind mount를 쓰는 이유

Plane 기본 구성은 데이터를 Docker named volume에 넣는다. 그러면 다른 데탑으로 옮길 때 volume 내부 경로를 찾아 docker run … tar로 퍼내야 한다. 이 배포는 네 곳을 전부 bind mount로 바꿨다.

컨테이너 경로호스트 경로내용
/var/lib/postgresql/data./data/pgdata업무 데이터 전체
/data./data/redis캐시
/var/lib/rabbitmq./data/rabbitmq큐
/export./data/uploads첨부파일

덕분에 백업과 이식이 폴더 복사로 끝난다. 로그 (logs_*)와 proxy 설정은 이식 대상이 아니라 named volume으로 남겼다. data/는 .gitignore에 있어 커밋되지 않는다.

다른 데탑으로 옮기기

docker compose down                      # 정합성 위해 정지 후 복사
rsync -avz ./ user@새데탑:/path/to/plane-image/

# 새 데탑에서 .env 4개 값을 새 IP로 수정
# APP_DOMAIN / WEB_URL / CORS_ALLOWED_ORIGINS / API_BASE_URL
docker compose up -d

URL에 포트를 빠뜨리지 말 것

APP_DOMAIN만 두고 http://${APP_DOMAIN} 식으로 쓰면 8080이 빠져서 프론트가 API를 엉뚱한 곳으로 찾는다. 네 값 모두 포트까지 명시한다.

운영 절차

모든 명령은 러너 데탑 WSL 안에서 실행

접속

ssh work@192.0.2.10   # Windows (관리자 권한 세션으로 뜬다)
wsl                      # WSL 진입, 기본 사용자 root
cd /home/plane/plane/plane-image

docker compose ps

백업

docker compose down
tar -czf /home/plane-backups/plane-data-$(date +%Y%m%d-%H%M%S).tar.gz data/

접속 점검

컨테이너 → localhost → LAN 순으로 어느 계층에서 막히는지 짚어주는 스크립트가 있다. 

bash shell-scripts/check_plane_access.sh              # 대상 데탑에서 전 계층
bash shell-scripts/check_plane_access.sh --lan-only   # 팀원 PC에서

LAN 접속이 끊겼을 때

재부팅으로 WSL IP가 바뀌면 portproxy가 어긋난다. 예약 작업이 자동으로 잡아주지만, 수동으로 다시 걸려면 Windows 관리자 PowerShell에서: 

powershell -ExecutionPolicy Bypass -File C:\plane-setup\setup_plane_lan_access.ps1 -RegisterTask

멱등하게 동작하므로 몇 번 실행해도 안전하다. -WhatIfOnly는 상태만 보고 아무것도 바꾸지 않는다.

업그레이드

  1. 정지 후 data/ 백업
  2. 새 릴리즈의 공식 compose를 받아 우리 변경분만 재적용한다 — 기존 파일을 패치하면 업스트림 변경을 놓친다 
    curl -sSL -o /tmp/new.yml \
  https://github.com/makeplane/plane/releases/download/vX.Y.Z/docker-compose.yml
  3. 새 릴리즈의 variables.env도 받아 신규 환경변수를 비교
  4. .env의 APP_RELEASE 변경 후 docker compose up -d

v1.4.2에서 실제로 물렸던 것

이 버전부터 compose 안의 SECRET_KEY / LIVE_SERVER_SECRET_KEY 하드코딩 fallback이 제거됐다. v1.2.1까지는 .env가 비어 있어도 동작했지만 이제는 아니다. 업그레이드 전에 두 값이 채워져 있는지 확인할 것.

god-mode 관리 콘솔

인스턴스 전역 설정 · 워크스페이스 관리와는 별개

http://192.0.2.10:8080/god-mode/general/

admin 컨테이너가 서빙하는 인스턴스 전체 관리 콘솔이다. 워크스페이스 안의 설정(프로젝트·멤버 권한 등)과는 층이 다르다 — 여기서 바꾸는 것은 이 서버에 올라온 모든 워크스페이스에 적용된다.

로그인 계정 체계도 별개다. API가 /api/instances/admins/sign-in/으로 분리되어 있어, 일반 Plane 로그인과 다른 인스턴스 관리자 자격으로 들어간다. 최초 설치 때 만든 관리자 계정이 이것이다.

API 경로용도
/api/instances/버전·에디션·설치 상태 공개
/api/instances/configurations/SMTP·인증 제공자·AI·이미지 설정
/api/instances/admins/인스턴스 관리자 계정
/api/instances/workspaces/이 서버의 워크스페이스 목록
/api/instances/email-credentials-check/SMTP 설정 검증

/api/instances/만 인증 없이 열려 있고 (버전 확인용) 나머지는 전부 401을 반환한다 — 확인 완료.

여기서 처리해야 할 것

  • 가입 차단 — 현재 enable_signup=true라 사내망 누구나 자기 계정을 만들 수 있다. 팀 6명만 쓰려면 가입을 막고 초대 방식으로 전환한다.
  • SMTP 확인 — 알림 메일이 실제로 나가는지 여기서 정해진다. 설정되어 있지 않으면 앱 내 알림만 뜨고 메일은 안 나간다. 이관 시 알림 폭탄 위험도가 여기에 달려 있으니 먼저 확인할 것.
  • 인증 제공자 — Google·GitHub·GitLab·Gitea 로그인을 붙일 수 있다. 현재는 이메일+비밀번호만 켜져 있다.

버전은 여기서 확인한다

UI로 확인하려면 god-mode 인스턴스 설정을 보고, 터미널이면 curl -s http://192.0.2.10:8080/api/instances/가 인증 없이 current_version과 latest_version을 돌려준다.

라이선스와 커스터마이즈

AGPL-3.0 · 코드 수정은 허용된다

Plane Community Edition은 AGPL-3.0이다 (LICENSE.txt 확인). 라이선스 키가 필요 없고, 무료이며, 버전 업그레이드만으로 유료 전환되지 않는다.

“코드 수정 금지”가 아니다

AGPL은 수정을 명시적으로 허용한다. 문제가 되는 것은 수정 자체가 아니라 수정본을 외부에 제공하는 것이다. 이 구분을 흐리면 정당한 사내 커스터마이즈까지 스스로 막게 된다.

핵심 조항은 §13 (Remote Network Interaction):

if you modify the Program, your modified version must prominently
offer all users interacting with it remotely through a computer
network ... an opportunity to receive the Corresponding Source
of your version by providing access ... at no charge

의무의 범위가 핵심이다 — “전 세계에 공개하라”가 아니라 “그것을 쓰는 그 사용자들에게 소스를 제공하라” 이다.

상황판단이유
사내 팀원만 사용문제 없음사내 GitLab에 소스가 있으면 충족 — fork를 사내에 두면 자동 준수
외부 협력사에 계정 발급주의그들도 “네트워크로 상호작용하는 사용자” → 소스 제공 의무 발생
타사에 서비스처럼 제공금지소스 제공 의무 + 상표 문제
수정본 바이너리 배포금지소스 동봉 의무

실질 규칙은 두 가지다.

  1. 코드를 수정하면 fork를 사내 GitLab에 두고 팀원이 접근 가능하게 유지한다
  2. 외부에 계정을 주거나 서비스처럼 제공하지 않는다

법률 자문이 아니다. 외부 제공이 논의되는 시점에는 법무 확인을 거칠 것.

소스 빌드로 전환하기

현재는 공식 이미지를 pull해서 쓴다. 코드를 고치려면 소스 빌드로 전환해야 한다. 빌드 정의는 deployments/cli/community/build.yml에 있고 이미지 6개를 만든다.

이미지소스스택

plane-spaceapps/spaceNext.js

API를 고치면 worker·beat-worker·migrator가 자동으로 따라온다 — 같은 이미지다.

setup.sh의 LOCAL_BUILD 경로를 쓰지 말 것

setup.sh에 LOCAL_BUILD=true → buildYourOwnImage() 경로가 있지만 옵션 1(Install)을 타므로 bind mount 설정이 날아간다. build.yml만 가져와 직접 빌드하고 compose의 이미지 태그만 바꿀 것.

실무 비용 — 라이선스보다 이쪽이 크다

  • 업그레이드가 매 릴리즈마다 rebase 작업이 된다. 지금은 .env 한 줄로 v1.2.1 → v1.4.2를 갔다
  • 보안 패치 추적이 늦어진다 — v1.4.0이 대규모 보안 배치였던 걸 생각하면 실질 위험
  • 이미지 6개 로컬 빌드(Next.js 4개 포함) — 시간·디스크 소모

코드를 고치기 전에 설정·환경변수·웹훅·REST API로 되는지 먼저 확인할 것. 확보한 77개 엔드포인트로 자동화는 대부분 커버된다. 태그는 APP_RELEASE=local보다 v1.4.2-custom.1처럼 upstream 버전을 남기는 편이 보안 패치 추적에 유리하다.

하지 말 것

되돌리기 어려운 작업

setup.sh 옵션 1(Install) / 5(Upgrade)

이 두 옵션은 Plane 공식 릴리즈에서 docker-compose.yaml을 새로 받아 덮어쓴다. 공식 파일은 v1.4.2에서도 여전히 named volume을 쓰므로, 실행하면 bind mount 설정이 날아가고 기존 데이터가 컨테이너에서 사라진 것처럼 보인다.

기동·정지는 docker compose를 직접 쓰고, setup.sh는 2(Start) / 3(Stop) / 4(Restart) / 6(Logs) / 7(Backup)만 쓴다.

업그레이드는 옵션 5 대신 위 운영 절차의 수동 절차를 따른다. setup.sh의 backupData()도 named volume 시절 방식이라 지금은 쓸 필요가 없다 — 폴더 복사가 곧 백업이다.

코드를 고치지 않고 켰다

Plane 소스에 drf-spectacular이 이미 들어 있고 ENABLE_DRF_SPECTACULAR 환경변수로만 잠겨 있었다 (plane/settings/common.py:565). .env에서 1로 켜고 compose의 x-app-env에 변수 통로만 뚫으면 된다. “코드를 고치기 전에 설정으로 되는지 먼저 본다”가 실제로 통한 사례다.

SCHEMA_PATH_PREFIX가 /api/v1/이고 preprocess_filter_api_v1_paths 훅이 걸려 있어 공개 REST API만 문서화된다. 웹앱 내부 API는 빠진다 — 이관 스크립트에 필요한 딱 그 범위다.

참고 — 스펙 없이 라우트만 뽑는 법

Swagger를 켜기 전에는 이 방법을 썼다. 스펙이 못 미더울 때 대조용으로 쓸 수 있다. 구동 중인 Django 앱의 URL resolver를 직접 순회하므로 지금 도는 코드 그 자체다. 다만 경로만 나오고 필드 스키마는 안 나온다. 

docker exec -i plane-image-api-1 python manage.py shell <<'PY'
from django.urls import get_resolver
from django.urls.resolvers import URLResolver
rows = []
def walk(res, prefix=''):
    for p in res.url_patterns:
        if isinstance(p, URLResolver):
            walk(p, prefix + str(p.pattern))
        else:
            rows.append(prefix + str(p.pattern))
walk(get_resolver())
for r in sorted(set(rows)):
    if 'v1/' in r:
        print(r)
PY

인증은 X-API-Key 헤더를 쓴다. 베이스 경로는 /api/v1/workspaces/{slug}/projects/{project_id}/… 형태다.

알림 폭탄 주의

v1.4.0부터 API로 생성한 작업 항목도 알림·이메일을 발송한다. 멤버를 초대해둔 상태에서 562건을 밀어 넣으면 전원에게 쏟아진다. 이관 전에 1~2건으로 실제 알림이 어떻게 나가는지 반드시 시험하고 순서를 정할 것.
